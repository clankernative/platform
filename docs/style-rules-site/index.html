Roc style rules

Roc's formatter is deliberately not configurable and the pinned compiler has no lint-plugin API, so our house style lives in a small reviewed patch against the native Zig formatter — not a second parser, a regex pass, or an SDK capability. These are the rules that patch adds, what they change, and why we took each one on.

FMT-1

Wrap at 120 columns

Implemented

No line exceeds 120 columns, indentation included. Tabs advance to four-column tab stops and a UTF-8 code point counts as one column. The formatter renders into a buffer, measures the actual columns it produced, and expands one explicit AST syntax group at a time until the output fits. It never reparses rewritten text or guesses from source-line lengths, and each retry expands a previously compact group, so the process terminates.

Upstream's formatter has no width policy at all: it preserves whatever the author wrote on one line. Pick a category to see the same input through both.

Why we did it

The first example is the case the width rule was built around: the platform's CommandDef record, which upstream leaves as a single 250-column line. Review happens in side-by-side diffs and terminal panes, and a rule that only some editors soft-wrap produces diffs nobody can read and merge conflicts that span an entire declaration. Fixing the width in the formatter rather than in a style guide means nobody negotiates it per file, and fmt --check makes it a build fact rather than review commentary.

FMT-2

Blank line between associated definition groups

Implemented

Inside an associated block — Type :: … .{ … } — each definition group is separated by one blank line. A matching signature and its implementation are one group and stay welded together. Constants, unannotated methods and nested types are groups too. The patch reuses the native formatter's own DefInfo and isPairedAnnoDecl grouping, which upstream already applies to top-level definitions, and extends it to the associated-statement loop; it is parser-driven, not line matching.

Before
Methods :: [].{
first : I64 -> I64
first = |value| value
second : I64 -> I64
second = |value| value
}
After roc-fmt-day2
Methods :: [].{
	first : I64 -> I64
	first = |value| value

	second : I64 -> I64
	second = |value| value
}

Upstream indents the block but leaves all four lines flush, so the two methods read as one wall of text.

Upstream roc fmt
Methods :: [].{
	constant = 42
	first = |value| value
	second = |value| value
}
After roc-fmt-day2
Methods :: [].{
	constant = 42

	first = |value| value

	second = |value| value
}

Unannotated methods and constants are separate groups; the rule does not depend on a signature being present.

Upstream roc fmt
Methods :: [].{
	Nested :: [].{
		first = 1
		second = 2
	}
	Empty :: [].{}
	last = 3
}
After roc-fmt-day2
Methods :: [].{
	Nested :: [].{
		first = 1

		second = 2
	}

	Empty :: [].{}

	last = 3
}

Nesting recurses. An empty associated block stays on one line and is still a group of its own.

Why we did it

Roc's associated blocks are where the platform's command and capability surfaces are defined, and they get long. Upstream already spaces top-level definitions this way, so compact associated blocks were an inconsistency in the same file rather than a deliberate style. Making the pair the unit — never splitting an annotation from its body — is what makes the blank line mean "new definition" instead of "new line of text". We deliberately did not add a maximum-spacing rule: an existing blank line inside a signature/body pair keeps upstream's behavior, so the patch stays small enough to propose upstream.

FMT-3

Comments keep their owner — including in empty blocks

Implemented

A leading comment belongs to the definition below it and moves with it across the inserted blank line. A trailing inline comment stays attached to the expression it follows, and a block's closing comment stays at the end. Separately, a comment-only associated block retains its comments — upstream silently deletes them.

Before
Empty :: [].{}

Comments :: [].{
# No definitions
}
Upstream comment lost
Empty :: [].{}

Comments :: [].{}
After roc-fmt-day2
Empty :: [].{}

Comments :: [].{
	# No definitions
}

The upstream pane is real output, not a hypothetical: formatting that file with the stock compiler destroys the comment.

Before
# First method
first : I64 -> I64
first = |value| value # First implementation
# Second method
second : I64 -> I64
second = |value| value
# End of methods
After roc-fmt-day2
	# First method
	first : I64 -> I64
	first = |value| value # First implementation

	# Second method
	second : I64 -> I64
	second = |value| value
	# End of methods

The blank line opens above # Second method, not between it and its method. The trailing # End of methods is not orphaned onto a new group.

Why we did it

A whitespace rule that silently relocates or deletes comments is worse than no rule — it makes people distrust the formatter and turn it off. The dropped comment-only block is upstream behavior, and losing a comment is a worse outcome than any spacing gain. The comment-aware separator (flushCommentsBeforeMin) was already in the native formatter, so keeping ownership correct cost us almost nothing.

FMT-4

Never break unbreakable content

Implemented

Strings, URLs, comments and identifiers that cannot be split without changing what they mean are left intact and may exceed 120 columns. The formatter only expands at legal parser boundaries; it is not a literal rewriter and not a comment reflow tool. There is no configurable width and no escape directive such as fmt: off.

After 124 columns, left alone
# https://example.com/segment/segment/segment/segment/segment/segment/segment/segment/segment/segment/segment/segment/
value =
	"https://example.com/segment/segment/segment/segment/segment/segment/segment/segment/segment/segment/segment/segment/"

The binding is still expanded onto its own line — everything that can legally break does — but the literal itself is untouched.

Exactly 120 columns unchanged
escalation = { primary_oncall: "platform", secondary_oncall: "control-plane", policy: "page-then-escalate", retries: 3 }
121 columns one character longer
escalation =
	{ primary_oncall: "platform", secondary_oncall: "control-plane", policy: "page-then-escalate-", retries: 3 }

The boundary is exact and regression-tested at 120 versus 121 columns, with tab stops and Unicode counting covered separately. Note how little moves: only the outermost group is expanded, and the record body stays inline because that alone is enough to fit.

Why we did it

A width rule that is allowed to edit literal content can change program behavior or break a URL in a doc comment, which is precisely the failure that makes teams distrust an auto-formatter. Refusing the break — and leaving one long line in the file — is the honest outcome. Refusing an escape directive is the same choice Roc made upstream: a per-file opt-out turns one rule into a negotiation on every review.

FMT-5

Digit grouping for long integer literals

Authored · not in installed binary

A plain decimal literal of five digits or more is rewritten with underscore separators every three digits. Four digits are left alone — those are usually years, ports or small counts that read better ungrouped. A literal that already contains an underscore is the author's chosen grouping and is kept exactly as written, and a based literal (0x, 0b, 0o) is left alone rather than grouped by the wrong convention.

Before
a = 1234
b = 12345
c = 1234567
d = 0xDEADBEEF
e = 12_345
Intended per the patch
a = 1234
b = 12_345
c = 1_234_567
d = 0xDEADBEEF
e = 12_345
Status check. integer-digit-grouping.patch is committed and its digest is pinned in toolchain.json as a build input, and build-formatter applies it after the spacing patch. The currently installed binary predates it — running it on the input above changes nothing — and roc_binary_sha256 still points at the spacing-only build, so a rebuild with both patches will not match the pin. This rule needs a rebuild, review and a new binary pin before it is real. The "intended" pane above is read from the patch, not from a run.

Why we did it

Magnitude errors in literals are the kind of bug that survives review because 10000000 and 100000000 look identical at a glance — and the platform's limits, budgets and timeouts are written as bare integers. Grouping makes an order-of-magnitude slip visible without anyone counting digits. Leaving authored underscores and based literals alone keeps the rule from fighting deliberate choices such as byte masks.

Invariants every rule is held to

  • The parse tree does not change. Regression tests serialize the AST before and after formatting, ignoring source positions, and require them to be identical. Formatting is whitespace policy, never a semantic edit.
  • Formatting is idempotent. Formatting an already formatted file produces byte-identical output; the width pass re-runs the check after every expansion.
  • Check mode never writes. fmt --check rejects compact definitions and overlong code without touching bytes, so it is safe in CI and in pre-commit paths.
  • Input that does not parse is rejected. Malformed source fails in both check and write mode and keeps its original bytes.
  • The toolchain is pinned end to end. Source commit, archive digest, Zig distribution, patch digests and the resulting binary hash are recorded in toolchain.json; xtask fmt verifies them before invoking anything, and a source build is never silently treated as a reviewed release.
  • The formatter is not the compiler. .toolchains/roc stays the unmodified application compiler for admission and glue; .toolchains/roc-fmt-day2 only formats.

Running it

From platform/
cargo run --locked -p xtask -- bootstrap-formatter   # verify pins, install reviewed binary
cargo run --locked -p xtask -- fmt-reports          # format platform sources + Reports
cargo run --locked -p xtask -- fmt-check-reports    # non-zero exit if anything is unformatted
cargo test --locked -p xtask formatter_native -- --ignored

# editor: external format command, document on stdin
.toolchains/roc-fmt-day2 fmt --stdin

Platform verification enforces formatting. Per-app isolated CI and build admission do not invoke this formatter yet — that gate is still planned, not delivered.

Short answer: we have no custom Roc lint rules today. One diagnostic is specified in detail and deliberately not implemented, and the verify-lint step you see in the pipeline is Rust linting, not Roc. This tab records both so the gap stays visible rather than being mistaken for coverage.

LINT-1

day2.definition-before-reference

Proposed · not implemented

References to named, function-valued definitions in the same module must appear after the implementation. That includes references passed as callbacks, not just calls: a signature above a use does not make an implementation below that use count as already defined. The rule would apply to module helpers and associated methods alike.

Direct self-recursion inside the current definition is allowed. Forward sibling references are rejected, which also rejects mutually recursive groups. Imports are exempt from the line-order comparison — two different files have no meaningful textual order — and Roc's existing local use-before-definition diagnostics stay as they are.

Would be rejected
# Rejected even though complete is passed as a value, not called here.
analyze = register_command(complete)

complete : Input -> Output
complete = |input| transform(input)
Fix
complete : Input -> Output
complete = |input| transform(input)

analyze = register_command(complete)

Schematic — register_command is not a new SDK capability. The fix moves the whole signature-and-implementation group above its use; the rule would not reorder anything automatically.

Why we wanted it

Reading a Roc module top to bottom should not require jumping forward to find out what a name means. Our command and capability modules are long and heavily callback-driven, where a forward reference is easy to introduce and hard to see in review. Rejecting mutual recursion as a side effect is intentional rather than incidental: direct self-recursion stays allowed, and a mutually recursive helper pair is treated as a sign that a module wants splitting.

Why it is not implemented

It cannot be done honestly at the level we have access to. Getting it right needs the compiler's own binding analysis: declaration identities retained through canonicalization, the actual binder behind every reference including callbacks and unused branches, and resolved dispatch targets for receiver calls like value.transform() — otherwise a local parameter that shares a name with a module function, or a same-named method on an unrelated type, reads as a violation. checked-types.json exports type shapes, not resolved source-reference identities, and the LSP symbol list is not a substitute. The verification receipt records this explicitly as "not implemented; pinned compiler metadata is insufficient" rather than shipping a regex approximation that would be wrong on exactly the cases that matter.

NOTE

What verify-lint actually runs

Implemented

The verify-lint step invoked by ops/Verify.roc is cargo clippy --locked --workspace --all-targets -- -D warnings. It lints the Rust platform crates and accepts no overrides. It says nothing about Roc source.

Roc source is covered today by formatting checks and by the platform's verification fixtures — not by any Roc-level semantic lint.

Why there is no plugin instead

Roc's formatter is intentionally not configurable, and the pinned compiler exposes no lint-plugin API. A Roc platform's runtime capability surface cannot install compiler diagnostics or formatting rules either, so an app-side hook is not available in principle. That leaves three options, and we chose the first: maintain a small reviewed patch set against the pinned compiler; write a second Roc parser and infer bindings from source text, which would disagree with the real compiler exactly where it matters; or build an external tool against the compiler's internals, which depends on unstable structures and still needs integration work to keep editor and build results equal. A formatter-only binary also cannot enforce a semantic rule — that has to reach compilation and admission, which is why LINT-1 is a bigger commitment than any of the formatting rules.

What delivering LINT-1 would require

  • Pin the rule, not just the compiler. Source commit, patch-set digest, build inputs and binary hash are pinned; app developers cannot supply plugins, compiler flags or rule toggles.
  • Check the authored snapshot. Run the diagnostic against the exact source accepted by a build, including authored SDK and fixture code. Exempt only host-proven generated or vendored inputs — not any directory that happens to be named generated.
  • Put the rule version in cache identity. A clean result from an older rule set must not admit a build under a newer one; invalidate or recheck the admitted bytes.
  • One tool everywhere. The same pinned binary in xtask fmt, fmt-check, build admission and the editor. Editor diagnostics are convenience; platform-owned build failure is enforcement.
  • Acceptance tests before policy. Earlier and later module functions and associated methods, qualified and receiver syntax, callbacks, aliases, shadowed parameters, nested scopes, earlier signatures with later bodies, self- and mutual recursion, unused branches, imports and generic dispatch — asserting the rule ID and both source locations, not merely that something failed to compile.
