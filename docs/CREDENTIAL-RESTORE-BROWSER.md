# Protected restore browser entry

The private command `day2 platform restore protected INSTANCE APP` prints
navigation DATA for the configured security origin. It does not authenticate an
administrator, approve a restore, send a restore request, open a browser or report
a completed restore. Final restore execution remains unavailable in this slice.

The operator opens that origin and uploads the bounded operator input on its
protected restore page. The URL carries no archive path, command input, approval
record, handoff or token. IAP is verified on every request; restore authorization
comes from the separate passkey ceremonies and native suppliers, never a CLI
actor argument or an approval flag.

The approver reviews the exact archive, target, epoch, executor and custody
selection. The browser asks the authenticator for user verification using a key
from the reviewed instance registry. A recorded approval is still not a
completed restore. The one-use handoff selects that same command and recorded
approval for the exact executor IAP email and subject; the approver and executor
may be the same person. It does not substitute for the executor's own passkey.
The executor explicitly requests its separate user-verifying ceremony, then
sends the assertion once through the already retained Shell connection. The
server spends that phase before invoking the native supplier. A rejected,
missing or unknown result cannot reconnect, repeat the send or recover the
ceremony from a browser-supplied identifier.

Browser sessions have a fixed five-minute UI lifetime. They do not renew native
action deadlines, challenges or the one-hour, single-use, nonrenewable approval
grant. Reloads, duplicate tabs, missing cookies and unknown responses cannot
reconstruct or retry a sent phase. A human wait retains only process-local
ceremony DATA and the admitted connection, with no action, stage, Current, SQL
or exclusion loan. Process loss requires a fresh ceremony rather than adoption
of an old locator.

The Controller's consuming join retains the accepting request's whole original,
peer, authenticated archive and writer through installation and finite output.
The Shell independently keeps its own request original and final checks. Before
returning output metadata, browser routing compares the approval request
commitment, operation, full archive, complete target and executor with the same
saved command. The request commitment differs from the whole signed approval
record's commitment. The installed digest is native-reported metadata, not a
client-verifiable authority grant, future readiness or proof of HTTP delivery.

The presentation also requires the complete closed target and digest fields in
the terminal metadata to match the executor's reviewed target before displaying
them. Missing, foreign or unknown fields remain an unknown result after the
single terminal send. The browser refuses epochs and binding generations that
JavaScript cannot represent exactly as positive safe integers; this is a UI
limitation, not a change to native integer bounds. These presentation checks do
not verify the approval signature or manufacture native installation evidence.

The native listener, peer admission and terminal packet suppliers still refuse
in this slice; no usable restore execution is enabled. A prompt, signed record,
ACK, HTTP status or printed URL cannot stand in for completed installation.

The private Controller-loop activation must join the genuine backend before
publication: mandatory bind currently propagates that backend's refusal. The
loop retains one session without reset or replacement, consumes the prepared
whole-owner continuation as its terminal return, then preserves the existing
active/peer refusal cleanup and the continuation's original result. Source
mutation checks pin that lifetime; they do not qualify an actual native peer.
