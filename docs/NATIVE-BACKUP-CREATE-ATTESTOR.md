# F fallback CREATE attestor — design, not deployment approval

The user approved parallel provider clarification and fallback design on November 26. The user sends PROVIDER-CONTRACT-QUESTIONS.md; this worker does not contact Google. All source work is local or draft review. No service, endpoint, resource, IAM, audit policy, key or workload is deployed.

## Chosen trust boundary

Put the narrow attestation logic inside the existing native-enrollment issuer, using its actual held KeyOwner and the SAME issuer certificate cohort already retained by the Controller. Use a new domain-separated CREATE-comparison signature only; do not add an enrolled role, generic signer, manual requester or source constructor. The separate required input is an authenticated **control-plane CREATE tap** with original identity and persisted outcome. It is not a Cloud Logging reader, admission webhook alone, Kubernetes watch or client-supplied receipt.

The tap must run at the API-server boundary, where it can preserve the original authenticated user before impersonation and join it, by exact request/audit identity, to the non-dry-run successful persisted response. Both the CronJob-controller Job CREATE and the Job-controller Pod CREATE are required. A standalone process reading current GKE objects cannot manufacture those missing facts. Availability of this hook on the current managed GKE service has NOT been established. If the provider offers no qualified hook/feed, operating this fallback would require an explicitly approved control-plane integration or a separately reviewed infrastructure change; a Deployment alone cannot solve it. No own-cluster move or scheduler replacement is implicit.

## Pair, completeness and identity

The proposed first profile deliberately requires authenticated durable arrival in Job-then-Pod order. Delayed/reversed/equal or missing members refuse; it does not reorder, retry or select a fresh attempt to regain admission. This may refuse legitimate delayed traffic; no liveness guarantee is claimed. That strict arrival predicate proves neither upstream creation causality nor feed completeness.

For each event retain an authenticated source channel/epoch and upstream request/stage identity plus the separate monotonic local journal sequence, audit/request ID, original and effective identity commitments, explicit qualified impersonation disposition, exact resource verb/kind/version, dry-run disposition, HTTP 201 and ResponseComplete, returned object UID, owner UID, and complete canonical persisted spec commitment. The actual tap must explicitly require upstream verb=create before constructing the fixed Create-only DATA variant; HTTP201 alone is not this predicate. Reject partial, omitted, split, truncated, unsupported/default-only or conflicting events. Equal names, annotations and spec labels do not replace actual UIDs.

The event spec commitments describe the complete persisted CREATE-time objects. They are not blindly equated to a later Running Pod spec: scheduler binding/defaulting can make that later object different. The future source profile must pin the exact supported CREATE-to-current derivation and all server-owned fields against the existing strict requester template/profile checks, retaining both complete objects/commitments. It may not erase unknown differences or reconstruct an unobserved CREATE from the current object. If that derivation or a full member is unavailable, refuse. The local comparison codec does not implement or qualify that producer.

Join Job to the exact configured CronJob UID and protected canonical scheduled slot, and Pod to that exact returned Job UID. Bind namespace and KSA UIDs, immutable cluster incarnation, CronJob/Job/Pod template commitments, admission/policy generation, full admitted intent/request/controller/connection/original commitments and both nonces. The scheduled slot stays the same stable reservation key across policy/key/feed rotation. No slot is reopened by a new attestation.

Completeness is **positive evidence for these two exact CREATEs**, not a claim that absence from a log proves nothing happened. The tap must explicitly certify original/effective fields are complete; Unknown is never treated as no impersonation. A local journal sequence cannot establish upstream completeness, authenticate a feed epoch or prove nonrollback continuity across restart. Those require an authenticated source restart/continuity anchor; until qualified, restart and every affected attempt stay closed. A missing RequestReceived or ResponseComplete, an audit gap affecting the pair, write uncertainty, conflicting duplicate, journal loss, restart without authenticated continuity or unsupported normalization permanently refuses that attempt. Exact duplicate deliveries may be recognized only by identical authenticated audit ID and normalized digest; they grant no new reservation or source action. Kubernetes blocking-strict is not treated as proof of successful ResponseComplete delivery: it only specifies request refusal on RequestReceived logging failure.

## Challenge and rotation

The issuer receives the challenge from its actual authenticated Controller exchange under the saved original; raw DATA cannot select an owner or clock. Only after joining the qualified complete historical pair to the current live requester chain, registry and exact held issuer certificate may it sign the fixed comparison. The reply binds that certificate digest, tap registry/profile/peer key/feed epoch, both event receipts, full binding, issuer challenge and exact request commitment. Later native original, physical/peer/authority checks and stable create-only slot reservation all remain mandatory.

Tap peer/key/feed rotation is an explicit reviewed registry change. New admissions use only the newly pinned generation. In-flight attempts retain their selected owners but fail when mandatory registry/cohort postchecks detect replacement; they are not renewed under the new key or original. Old event journal content cannot silently cross epochs. No fallback to an old key, a second parser, a renamed cluster or a new slot. Issuer key rotation follows the same existing certificate/root process; no packet chooses a trusted key. Signing and journal failures remain Unknown/refused and do not allow automatic recapture.

## Local code boundary

First code is fixed, bounded **comparison DATA only**, using existing signature framing and canonical identity codecs. Re-signed negative tests cover every binding, original-versus-effective identity, unknown impersonation, dry-run/failure/early stage, journal epochs/order and cohort/challenge replay. No tap client, network listener, journal writer, deployment, IAM, real requester or accepting ProtectedScheduledCreate constructor is added. The existing Infallible supplier remains closed. Mechanical signature success is not qualification of this proposed TCB.

## Primary source limits

[Kubernetes audit Event](https://kubernetes.io/docs/reference/config-api/apiserver-audit.v1/) defines original user and impersonatedUser separately and carries request/response stages. [Audit backend modes](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/#event-batching) describe RequestReceived fail-closed behavior and asynchronous drop limits; they do not guarantee complete response delivery. [Admission requests](https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/#request) describe the pre-persistence admission seam. These are interface facts, not proof the proposed tap is installed or available in managed GKE. The current GKE provider-origin and conversion guarantees remain the subject of the user's support questions.
